# Перенос бота на новый сервер (37.27.13.102)

## Важно: что на самом деле переносим

Бот на VPS **не хранит данные локально**. Вся база данных, файлы-доказательства
и хранилище — в облаке **Supabase** (не на сервере). `docker-compose.yml` не
монтирует volume'ы, поэтому в контейнере нет персистентных данных.

Значит переносить нужно только:

1. **Код** — через GitHub (публичный/приватный репозиторий с токеном).
2. **Секреты** — файл `.env` со старого сервера (в git не хранится, `.gitignore`).

БД, файлы отзывов, пользователи — трогать не нужно: они уже в Supabase Cloud и
будут доступны новому серверу сразу после того, как в `.env` попадут те же
`SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`.

Сайт (`web/`) на Vercel — не мигрирует, он не на этом VPS.

---

## Шаг 0 — проверка на старом сервере

Подключитесь к старому серверу и убедитесь, что там **действительно только бот**
(без дополнительных сервисов вроде nginx/cron, о которых вы не упомянули):

```bash
ssh user@СТАРЫЙ_IP
cd /opt/rental-reviews-bg
docker compose ps
cat .env   # запомните/скопируйте значения — понадобятся ниже
```

Если там есть что-то ещё кроме контейнера `rental-reviews-bot` — сообщите,
это не покрыто инструкцией ниже.

---

## Шаг 1 — скачать `.env` со старого сервера через WinSCP

1. Откройте WinSCP → подключение по SFTP к старому серверу.
2. Перейдите в `/opt/rental-reviews-bg/`.
3. Скачайте файл `.env` на Windows, например в
   `C:\Users\Vlad\Downloads\rental-reviews-bg.env`.

> Это единственный файл со старого сервера, который реально нужен новому серверу.
> Всё остальное (код) возьмём из GitHub.

---

## Шаг 2 — подготовить новый сервер (37.27.13.102)

```bash
ssh user@37.27.13.102
```

Проверьте, что Docker и sudo уже работают (по вашим словам — да):

```bash
docker --version
docker compose version
```

`/opt` принадлежит `root` — сначала создайте папку и отдайте её своему
пользователю, иначе будет `Permission denied`:

```bash
sudo mkdir -p /opt/rental-reviews-bg
sudo chown $USER:$USER /opt/rental-reviews-bg
```

Клонируйте репозиторий (используйте **новый** токен — старый, который
был показан в чате, нужно отозвать на github.com/settings/tokens и
выпустить заново, см. примечание в конце шага):

```bash
cd /opt
git clone https://<ВАШ_НОВЫЙ_ТОКЕН>@github.com/Lightwell-bg/rental-reviews-bg.git rental-reviews-bg
cd rental-reviews-bg
```

> Токен подставляется только в момент клонирования и попадает в `git remote -v`
> в открытом виде. После клонирования замените remote на чистый URL, чтобы
> токен не светился в конфиге репозитория:
> ```bash
> git remote set-url origin https://github.com/Lightwell-bg/rental-reviews-bg.git
> ```
> При следующем `git pull` Git спросит логин/пароль (или настройте
> [credential helper](https://git-scm.com/docs/gitcredentials), или используйте
> Personal Access Token как пароль при запросе).
>
> **Токен, который был вставлен в чат ранее, считается скомпрометированным** —
> отзовите его на [github.com/settings/tokens](https://github.com/settings/tokens)
> и используйте здесь новый.

## Шаг 3 — залить `.env` на новый сервер через WinSCP

1. В WinSCP подключитесь теперь к **новому** серверу `37.27.13.102`.
2. Перейдите в `/opt/rental-reviews-bg/`.
3. Загрузите (drag-and-drop) скачанный на шаге 1 файл `.env` в эту папку.

Проверьте на сервере, что файл на месте и без искажений (WinSCP иногда меняет
перевод строк — выбирайте бинарный/текстовый режим Auto):

```bash
cd /opt/rental-reviews-bg
ls -la .env
cat .env   # сверьте с тем, что было на старом сервере
```

## Шаг 4 — остановить бота на старом сервере (важно, до запуска нового)

Telegram Bot API не позволяет двум процессам с одним `TELEGRAM_BOT_TOKEN`
одновременно держать polling — будет ошибка `conflict`. Поэтому сначала
глушим старый:

```bash
ssh user@СТАРЫЙ_IP
cd /opt/rental-reviews-bg
docker compose down
```

(Опционально, чтобы бот не поднялся сам при перезагрузке старого сервера:
`docker compose down` уже достаточно — `restart: unless-stopped` не переживёт
явный `down`.)

---

## Шаг 5 — запустить бота на новом сервере

```bash
ssh user@37.27.13.102
cd /opt/rental-reviews-bg
docker compose up -d --build
docker compose logs -f bot
```

Ждите в логе строку:

```
Бот запущен (polling)
```

Нажмите `Ctrl+C`, чтобы выйти из просмотра логов (контейнер продолжит работать).

## Шаг 6 — проверка

- [ ] `docker compose ps` на новом сервере — контейнер `rental-reviews-bot`, статус `Up`
- [ ] В Telegram: `/start` боту — отвечает
- [ ] Оставить тестовый отзыв через бота — появляется в Supabase → Table Editor → `reviews`
- [ ] Админам приходит уведомление в Telegram
- [ ] `/admin` в боте открывается (для ID из `ADMIN_TELEGRAM_IDS`)
- [ ] Сайт на Vercel (`reviews.bginfo.eu` или ваш домен) как обычно видит те же данные (Supabase общий) — открыть `/reviews`, `/admin` на сайте

Если что-то не работает — проверьте `docker compose logs -f bot` на новом сервере
на предмет ошибок авторизации Supabase/Telegram (обычно из-за опечатки при
переносе `.env`).

---

## Шаг 7 — старый сервер

После того как всё в чек-листе шага 6 подтверждено:

```bash
ssh user@СТАРЫЙ_IP
cd /opt/rental-reviews-bg
docker compose down   # если ещё не сделали на шаге 4
docker system prune -f   # опционально, освободить место (образы/кэш бота)
```

Сам сервер можно выключать/удалять у провайдера — код и секреты уже
перенесены, данные не терялись (они всегда были в Supabase).

## Итог: что не нужно было мигрировать и почему

| Компонент | Где живёт | Нужно ли переносить |
|---|---|---|
| База данных, отзывы, пользователи | Supabase Cloud | Нет — облако, не привязано к серверу |
| Файлы-доказательства | Supabase Storage | Нет — облако |
| Сайт (web/) | Vercel | Нет — деплоится из GitHub напрямую |
| Код бота | GitHub | Да — `git clone` на новом сервере |
| Секреты (`.env`) | Только на серверах | Да — единственное, что физически переносили |
